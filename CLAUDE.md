## Контекст работы

- **Пользователь:** опытный backend-разработчик (Node.js, Go, Postgres, Docker); в LLM, мульти-агентных системах, графах знаний, онтологиях и векторном поиске опыта меньше — эти области объясняй подробнее.
- **Стиль:** двигайся поэтапно, сверяйся на стыках крупных тем, объясняй решения и trade-offs.

## Технические решения

- **БД и память:** Postgres + pgvector (вместо Zep Cloud) — экономия, всё в одной БД
- **Симулятор:** свой минимальный движок на Go (вместо camel-oasis). Если упрёмся в масштаб — fallback на OASIS через отдельный Python-сервис
- **Архитектура:** Node.js (backend API) ↔ Go (симулятор) ↔ Postgres
- **LLM:** абстракция OpenAI-совместимого API. Для разработки — Ollama локально (Qwen2.5:14b на MacBook M2 Pro), для prod — переключение через env

## Процесс разработки и агенты

- Когда пользователь просит написать код — после написания вызвать агента `tester` (пишет unit-тесты, jest, мокает IO).
- **Жёсткая проверка:** Stop-hook (`.claude/hooks/verify-on-stop.sh`) перед завершением прогоняет `lint` + `test:unit`, если менялся `api/src`, и не даёт закончить пока не зелено. Плюс PostToolUse-hook линтит каждый изменённый `api/**/*.ts` сразу.
- Пуш в GitHub делает пользователь сам. Когда просит проверить упавший CI — вызвать `ci-doctor`: механику (lint/format/yml) чинит сам, логику (баг в коде/тесте) только диагностирует и предлагает.
- `reviewer` — по запросу, ревью диффа против конвенций (read-only).

## Что НЕ предлагать

- Платные внешние сервисы для core-функциональности (Zep, OpenAI-only)
- Готовые движки вместо своей реализации (OASIS как первое решение, а не fallback)
