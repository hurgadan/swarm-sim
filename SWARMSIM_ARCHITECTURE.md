## Часть 1. Архитектура

### 1.1 Высокоуровневая схема

```
┌─────────────────┐         ┌──────────────────────┐         ┌─────────────────┐
│                 │  HTTP   │                      │  HTTP   │                 │
│   Nuxt.js       │◄───────►│   NestJS (API)       │◄───────►│  Go-Simulator   │
│   (frontend)    │  SSE/WS │   TypeScript         │   REST  │  (микросервис)  │
│                 │         │                      │         │                 │
└─────────────────┘         └──────────┬───────────┘         └────────┬────────┘
                                       │                              │
                                       │                              │
                                       ▼                              ▼
                            ┌──────────────────────┐       ┌──────────────────┐
                            │   Postgres           │       │  OpenAI API      │
                            │   + pgvector         │       │  (или совмест.)  │
                            └──────────────────────┘       └──────────────────┘
                                       ▲
                                       │
                            ┌──────────┴───────────┐
                            │   Go-Simulator       │
                            │   пишет напрямую     │
                            └──────────────────────┘
```

### 1.2 Ответственности сервисов

**Nuxt.js (frontend)**
- UI: загрузка файлов, визуализация графа, таймлайн симуляции, просмотр отчёта, чат с агентами
- Получение real-time обновлений (SSE или WebSocket от NestJS)
- Никакой бизнес-логики — только рендер и отправка запросов

**NestJS (главный бэкенд)**
- REST API для фронтенда
- Вся работа с LLM для *подготовительных* шагов: онтология, извлечение сущностей, генерация профилей, ReACT-агент для отчёта
- Хранение состояния: проекты, онтологии, граф, профили, отчёты
- Оркестрация: запускает симуляцию в Go-сервисе, опрашивает статус, получает результаты
- Стриминг прогресса на фронт

**Go-Simulator (отдельный сервис)**
- Только симуляция агентов в виртуальной соцсети
- Горутины для параллельного выполнения агентов
- Цикл раундов, логирование действий
- REST API: `POST /simulate/start`, `GET /simulate/:id/status`, `POST /simulate/:id/stop`
- Пишет действия напрямую в Postgres (меньше накладных расходов, чем гонять через NestJS)
- **Почему Go, а не NestJS:** симуляция сотен параллельных агентов — это I/O-bound (много параллельных запросов к LLM) плюс CPU-bound (обработка состояния). Go с горутинами делает это намного эффективнее и проще, чем Node.js.

**Postgres + pgvector**
- Единая БД для всего
- Расширение `pgvector` добавляет тип `vector` и индексы для семантического поиска
- Пишет и NestJS, и Go-simulator

### 1.3 Коммуникация между сервисами

**Nuxt ↔ NestJS**
- REST для запросов-ответов
- Server-Sent Events (SSE) для стриминга прогресса (удобнее чем WebSocket, работает по HTTP)

**NestJS ↔ Go-Simulator**
- Простой REST. Очередь (RabbitMQ/Redis) пока не нужна — симуляции запускаются пользователем и не так часто
- NestJS опрашивает статус (polling), либо Go шлёт webhook на NestJS когда раунд завершён

**Сервисы ↔ Postgres**
- Прямые коннекты. Go пишет в те же таблицы, что и NestJS — схема одна

**Сервисы ↔ LLM**
- Официальные SDK: `openai` для Node.js в NestJS, `go-openai` для Go

### 1.4 Схема БД (Postgres)

Упрощённая схема, без индексов и FK для наглядности:

```sql
-- Проекты и исходный материал
projects         (id, name, status, created_at)
documents        (id, project_id, filename, content_text, parsed_at)

-- Онтология (что за типы сущностей в этом мире)
ontologies       (id, project_id, entity_types jsonb, relation_types jsonb, llm_version)

-- Граф знаний
entities         (id, project_id, type, name, attributes jsonb, embedding vector(768))
relations        (id, project_id, from_entity_id, to_entity_id, type, attributes jsonb)

-- AI-агенты (сгенерированные из сущностей)
agent_profiles   (id, entity_id, biography, personality, interests jsonb, created_at)

-- Симуляции
simulations      (id, project_id, status, config jsonb, started_at, finished_at)
simulation_rounds(id, simulation_id, round_number, virtual_time, summary, created_at)
simulation_actions(
  id, simulation_id, round_id, agent_profile_id,
  action_type,  -- 'post' | 'reply' | 'like' | 'repost' | 'follow'
  content text,
  target_action_id nullable,
  created_at
)

-- Отчёты и чат
reports          (id, simulation_id, content_md, llm_trace jsonb, created_at)
report_chats     (id, report_id, role, content, created_at)
```

**Ключевые моменты:**
- `embedding vector(768)` — это pgvector-поле. 768 = размерность эмбеддингов `nomic-embed-text` (Ollama). При переходе на OpenAI `text-embedding-3-small` нужно будет пересчитать все эмбеддинги и сменить на `vector(1536)`
- Поиск: `SELECT * FROM entities ORDER BY embedding <=> $query_embedding LIMIT 10` — даст семантически похожие сущности
- `attributes jsonb` — всё что не влезло в структурированные колонки (гибкость)
- `llm_trace jsonb` — лог того, какие инструменты вызывал ReACT-агент при генерации отчёта (полезно для дебага)

### 1.5 Стратегия памяти агентов

**MVP: pgvector в Postgres**
- Все эмбеддинги и поиск в той же БД
- Простой SQL-запрос даёт семантический поиск
- Никаких внешних зависимостей — удобно для проекта

**Когда переходить на Zep Cloud:**
- Граф стал большой (десятки тысяч сущностей) — pgvector начинает тормозить без тонкой настройки индексов
- Нужна **temporal reasoning** — факты с временной валидностью («Анна была CTO с 2020 по 2023»), Zep это делает из коробки
- Нужен production-grade retrieval с решардингом, репликацией, SLA
- Для проекта этого не нужно — pgvector справится

## Часть 2. Глоссарий AI-терминов для бэкендера

Короткий разбор терминов, которые встретятся в плане. Если что-то знакомо — пропускай.

### LLM (Large Language Model)
Нейросеть, которая предсказывает следующий токен по контексту. Для нас — просто HTTP API: отправил текст → получил текст. Примеры: GPT-4o, Claude, Qwen, DeepSeek.

### Токены
LLM не видит буквы — она видит «токены» (куски слов). Примерно 1 токен ≈ 0.75 слова на английском, 1.5–2 токена на слово на русском. Важно потому что:
- **Контекстное окно** — сколько токенов помещается в один запрос (у GPT-4o ~128k, у современных моделей до 1M)
- **Стоимость** — тарификация идёт за токены ввода и вывода отдельно

### Эмбеддинги
Текст → вектор из чисел (обычно 768, 1536 или 3072 чисел). Смысл: два семантически близких текста будут близки в векторном пространстве. Типа хеш, но сохраняющий смысл.

Пример:
```
"собака" → [0.23, -0.11, 0.87, ...]
"пёс"    → [0.25, -0.09, 0.85, ...]  // близко к "собаке"
"машина" → [-0.44, 0.71, 0.12, ...]  // далеко
```

**Зачем:** семантический поиск. Вместо `WHERE name LIKE '%пёс%'` делаешь «найди топ-10 самых похожих по смыслу».

### Векторный поиск и pgvector
Постгрес с расширением `pgvector` умеет хранить эмбеддинги и искать ближайшие. Три метрики расстояния: L2, inner product, cosine. Для текстовых эмбеддингов обычно cosine (`<=>` в SQL).

### Промпт и роли (system/user/assistant)
Запрос к LLM — это массив сообщений с ролями:
- `system` — инструкция «кто ты и как себя ведёшь»
- `user` — сообщение от пользователя
- `assistant` — предыдущий ответ модели (для диалога)

```json
[
  {"role": "system", "content": "Ты эксперт по текстам. Извлекай сущности."},
  {"role": "user", "content": "Проанализируй: ..."}
]
```

### Few-shot prompting
Дать LLM 2–5 примеров «вход → выход» прямо в промпте. Резко повышает качество без всякого fine-tuning. В SwarmSim так делаем онтологию и извлечение сущностей.

```
Пример 1: "Apple выпустила iPhone" → {entities: [Apple, iPhone], relation: выпустила}
Пример 2: ...
Теперь ты: "{новый текст}"
```

### RAG (Retrieval-Augmented Generation)
Паттерн: перед ответом на вопрос — найди релевантные куски из базы (векторным поиском) и вставь их в промпт. LLM отвечает уже с учётом этих данных.

```
Вопрос → эмбеддинг → поиск в pgvector → топ-5 документов → вставляем в промпт → LLM отвечает
```

### GraphRAG
То же самое, но база — это граф знаний, а не плоский список документов. Запросы идут к узлам и связям. Позволяет отвечать на вопросы типа «кто связан с X через двух посредников».

### Tool calling (function calling)
Возможность LLM вызывать твои функции. Ты описываешь функцию в JSON-схеме, LLM решает когда её вызвать и с какими аргументами, ты выполняешь, возвращаешь результат, LLM продолжает.

```json
{
  "name": "search_graph",
  "description": "Ищет сущности в графе по запросу",
  "parameters": { "query": "string" }
}
```

LLM вместо текстового ответа может вернуть: `{"tool_call": "search_graph", "args": {"query": "сотрудники"}}`. Ты выполняешь, отдаёшь результат обратно.

### ReACT (Reasoning + Acting)
Паттерн для агентов: LLM в цикле думает → вызывает инструмент → получает результат → думает снова → ... → даёт финальный ответ. По сути это tool calling, обёрнутый в цикл с инструкцией «работай пока не решишь задачу».

### AI-агент (vs обычный вызов LLM)
**Обычный вызов:** запрос → ответ, всё.
**Агент:** LLM + память + инструменты + цикл принятия решений. Может многократно дёргать инструменты, хранить состояние, работать долго.

В SwarmSim **два разных агента:**
1. Симуляционные агенты (в Go-сервисе) — каждый представляет персонажа, живёт в соцсети
2. ReACT-агент для отчёта (в NestJS) — аналитик, исследующий граф и симуляцию через инструменты

## Часть 3. Пошаговый план реализации

7 этапов. Каждый заканчивается рабочей фичей — можно остановиться на любом и иметь что-то полезное.

### Этап 0. Скелет инфраструктуры (1–2 дня)

**Цель:** все сервисы запускаются, видят друг друга, подключены к БД.

**Задачи:**
- Монорепо: `/apps/web` (Nuxt), `/apps/api` (NestJS), `/apps/simulator` (Go)
- `docker-compose.yml`: Postgres 16 с расширением pgvector (образ `pgvector/pgvector:pg16`)
- `.env.example` с ключами (OpenAI API, DB creds)
- NestJS: пустое приложение, health-check `/api/health`
- Nuxt: главная страница с кнопкой «Health check» которая дёргает API
- Go: HTTP-сервер с `/health`, подключение к Postgres
- Миграции БД (рекомендую `node-pg-migrate` или `drizzle-kit` для NestJS-части). Go использует те же миграции.
- Скрипт `make dev` или `docker-compose up` который поднимает всё разом
- Установить Ollama и скачать локальные модели для разработки — см. [SWARMSIM_LLM_PROVIDERS.md](SWARMSIM_LLM_PROVIDERS.md)

**Готово когда:** открываешь Nuxt в браузере, нажимаешь кнопку — видишь «API OK, DB OK, Simulator OK».

---

### Этап 1. Загрузка текста и генерация онтологии (3–5 дней)

**Цель:** пользователь грузит файл, система через LLM вычисляет какие типы сущностей в нём есть.

**Что реализуем:**

Фронтенд:
- Страница «Новый проект»: поле имени, загрузка файла (.txt, .md, .pdf)
- Страница проекта: показываем содержимое документа и сгенерированную онтологию

Бэкенд (NestJS):
- `POST /projects` — создание проекта
- `POST /projects/:id/documents` — загрузка файла, парсинг PDF (например через `pdf-parse`), сохранение текста
- `POST /projects/:id/ontology/generate` — вызов LLM с few-shot промптом, возвращает структуру `{entity_types: [...], relation_types: [...]}`
- `GET /projects/:id/ontology` — чтение

Промпт для онтологии: system-сообщение с ролью «ты аналитик», 2–3 примера «текст → онтология», и инструкция выделить именно 8–10 типов сущностей. LLM возвращает JSON.

**Ключевой приём:** использовать **structured outputs** OpenAI (`response_format: { type: "json_schema" }`) — так LLM гарантированно вернёт валидный JSON нужной структуры.

**Готово когда:** грузишь файл → видишь сгенерированную онтологию в UI.

---

### Этап 2. Извлечение сущностей и построение графа (1 неделя)

**Цель:** из текста по онтологии вытащить конкретные узлы и связи, визуализировать граф.

**Что реализуем:**

Бэкенд:
- Chunking: разбить большой текст на куски по ~2000 токенов (библиотека `llamaindex` или ручной split по предложениям)
- Для каждого чанка — LLM-запрос с онтологией и инструкцией «извлеки сущности и связи в этом формате JSON»
- Дедупликация: если «Анна Петрова» встречается в нескольких чанках — это одна сущность. Матчить по имени + эмбеддинг-similarity (порог например 0.9)
- Для каждой сущности считаем эмбеддинг (`text-embedding-3-small`) и сохраняем в pgvector
- `POST /projects/:id/graph/build` — запускает всё это в фоне
- `GET /projects/:id/graph` — возвращает все узлы и рёбра (с пагинацией если много)
- SSE-эндпоинт `/projects/:id/graph/progress` для прогресса

Фронтенд:
- Визуализация графа. Варианты: [vis-network](https://github.com/visjs/vis-network) (проще) или D3.js (гибче). Для проекта **vis-network** — быстрее поднять
- Клик по узлу → боковая панель с деталями сущности
- Фильтры по типам сущностей

**Готово когда:** из загруженного текста строится граф из десятков узлов, его можно крутить в браузере.

---

### Этап 3. Генерация профилей агентов (3–5 дней)

**Цель:** каждая сущность (человек) превращается в проработанного AI-персонажа.

**Что реализуем:**

Бэкенд:
- `POST /projects/:id/profiles/generate` — для каждой сущности-«персоны» в графе:
  - Собираем её контекст: её атрибуты + эмбеддинг-поиск по связанным фактам из графа
  - Вызываем LLM: «Придумай биографию, характер, MBTI, интересы, цели для этого персонажа»
  - Сохраняем в `agent_profiles`
- `GET /projects/:id/profiles` — список
- `PATCH /profiles/:id` — ручное редактирование (пользователь может допилить)

Фронтенд:
- Страница «Персонажи»: карточки всех агентов с фото-заглушкой, биографией
- Редактор профиля: форма для правок

**Готово когда:** после билда графа — получаешь список проработанных персонажей, можешь их отредактировать.

### Этап 4. Go-сервис симуляции (1–2 недели) — самая мясная часть

> 📖 Подробная реализация с кодом: **[SWARMSIM_DEEPDIVE.md → Часть A. Go-Simulator](SWARMSIM_DEEPDIVE.md#часть-a-go-simulator)**

**Цель:** все агенты живут в виртуальной соцсети и ведут себя достоверно.

**Архитектура Go-сервиса:**

```
Simulator
├── HTTP API (chi router или Gin)
├── Core
│   ├── SimulationEngine  — запускает раунды
│   ├── AgentPool         — все активные агенты
│   ├── SocialNetwork     — лента, подписки, лайки, посты
│   └── LLMClient         — обёртка над OpenAI SDK
├── Storage (Postgres)
└── Logger (JSONL + БД)
```

**Модель симуляции:**

```go
type Agent struct {
    ID          string
    ProfileID   string
    Biography   string
    Personality string
    Following   []string  // на кого подписан
    RecentFeed  []Action  // что недавно видел
}

type Action struct {
    AgentID    string
    Type       string  // post | reply | like | repost | follow
    Content    string
    TargetID   *string
    Timestamp  time.Time
}
```

**Цикл симуляции:**

```
Для каждого раунда (1..N):
  Для каждого агента параллельно (горутины + semaphore на 10-20 одновременных LLM-вызовов):
    1. Собрать контекст: профиль + лента (последние 20 действий от подписок)
    2. Вызвать LLM с промптом "что ты сделаешь?" (tool calling: post/reply/like/skip)
    3. Получить действие
    4. Записать в БД + обновить ленты других агентов
  После всех агентов: саммари раунда через LLM, сохранить в simulation_rounds
```

**Важные детали:**
- **Rate limiting:** OpenAI имеет лимиты RPM. Использовать пакет типа `golang.org/x/time/rate` для троттлинга
- **Параллелизм:** semaphore/worker pool на N горутин (не сотни параллельных LLM-вызовов сразу, иначе rate limit)
- **Идемпотентность:** если сервис упал посреди раунда — уметь продолжить с места падения (писать статус раунда в БД)

**Коммуникация с NestJS:**
- NestJS: `POST http://simulator:8080/simulate` с `{simulation_id, config, profiles_snapshot}`
- Go: возвращает `202 Accepted`, запускает симуляцию в горутине
- Go: по окончании раунда пишет в `simulation_rounds` и в лог-файл
- NestJS поллит `GET /simulate/:id/status` и стримит прогресс на фронт через SSE

Фронтенд:
- Страница «Симуляция»: настройки (количество раундов, триггерное событие)
- Live-таймлайн: действия появляются в реальном времени
- Карточки с последними постами

**Готово когда:** запускаешь симуляцию, видишь как агенты пишут посты, реагируют друг на друга, всё это отображается в live-режиме.

### Этап 5. Генерация отчёта (ReACT-агент) (1 неделя)

> 📖 Подробная реализация с кодом: **[SWARMSIM_DEEPDIVE.md → Часть B. ReACT-агент](SWARMSIM_DEEPDIVE.md#часть-b-react-агент-для-отчёта-nestjs)**

**Цель:** аналитический отчёт, сгенерированный AI, который самостоятельно исследует результаты.

**Что реализуем:**

В NestJS строим ReACT-агента с инструментами:
- `search_graph(query: string)` — семантический поиск по графу
- `get_agent_actions(agent_id, filter)` — все действия конкретного агента
- `get_round_summary(round_number)` — саммари раунда
- `interview_agent(agent_id, question)` — спросить у симулированного агента в его характере
- `get_top_posts(metric)` — топ постов по лайкам/репостам

**Реализация цикла:**

```typescript
async function generateReport(simulationId: string) {
  const messages = [{role: 'system', content: REPORT_AGENT_PROMPT}];
  let finalReport = null;

  while (!finalReport) {
    const response = await openai.chat.completions.create({
      model: 'gpt-4o',
      messages,
      tools: TOOLS_SCHEMA,
      stream: true,  // стримим на фронт
    });

    if (response.choices[0].message.tool_calls) {
      // LLM хочет вызвать инструмент
      for (const call of tool_calls) {
        const result = await executeTool(call);
        messages.push({role: 'tool', content: result, tool_call_id: call.id});
      }
    } else {
      // LLM вернула финальный отчёт
      finalReport = response.choices[0].message.content;
    }
  }

  await saveReport(simulationId, finalReport);
}
```

Фронтенд:
- Страница «Отчёт»: markdown с подсветкой синтаксиса (библиотека `@nuxtjs/mdc` или `marked`)
- Пока генерируется — показываем стрим и trace (какие инструменты вызывает агент, — это очень круто смотрится)

**Готово когда:** после симуляции нажимаешь «Сгенерировать отчёт», смотришь как агент роется в данных и выдаёт markdown-анализ.

## Замечания по разработке

1. **LLM недетерминирована.** Не пиши тесты, которые сравнивают конкретные строки от LLM. Тестируй структуру («вернулся валидный JSON», «есть хотя бы 3 сущности»).

2. **LLM ошибается.** Всегда имей fallback: если LLM вернула мусор — ретрай, если снова мусор — логируй и показывай пользователю понятную ошибку.

3. **Стоимость контролируй с первого дня.** Записывай в логи потребление токенов. Лимиты OpenAI включай на уровне ключа.

4. **Начинай с маленьких симуляций.** 5 агентов × 3 раунда — проверить что цикл работает. Потом масштабируй.

5. **Структурные ответы > текстовые.** Везде где можно — `response_format: json_schema`. Парсить markdown из LLM — ад.

6. **Не экономь на логах.** Логируй каждый LLM-вызов целиком (prompt + completion + usage). Это 90% успеха дебага агентных систем.
